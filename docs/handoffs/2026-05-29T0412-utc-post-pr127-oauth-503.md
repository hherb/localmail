## Project context (1-minute version)

`localmail` mirrors IMAP accounts (Gmail OAuth, password) into Postgres.
**Strictly read-only with respect to IMAP**. Downstream consumers read
the DB + attachment tree directly or via the `localmail serve` HTTPS API.
The Tauri 2 + Svelte 5 desktop GUI lives at [gui/](gui/). The HTTPS
admin UI (Sub-plans 1 + 2A to date — auth scaffolding, session
revocation, account management + web OAuth) ships under
[src/localmail/serve/admin/](src/localmail/serve/admin/) and
[src/localmail/api/admin/](src/localmail/api/admin/), with the
end-to-end design captured in

### The #126 fix (PR #127 — open)

- **Problem:** `oauth.py::_build_flow` raised a bare `RuntimeError`
  when `gmail_oauth.client_secrets_file` was unset; the `oauth_start`
  route (`POST /v1/admin/accounts/{id}/oauth/start`) only caught
  `NotFound` / `AccountFieldError`, so the RuntimeError escaped as a
  **500**. That's operator misconfiguration, not a server bug — a 500
  reads as "the server is broken."
- **Fix:** new typed `OAuthNotConfigured(RuntimeError)` in
  [src/localmail/api/admin/oauth.py](src/localmail/api/admin/oauth.py),
  raised by `_build_flow`; `oauth_start` in
  [src/localmail/serve/admin/oauth_router.py](src/localmail/serve/admin/oauth_router.py)
  maps it to a clean **503** with detail "Gmail OAuth is not
  configured on this server".
- **Subclass choice:** subclasses `RuntimeError` so the OAuth
  *callback*'s broad `except Exception` still catches it as a
  failed-redirect (the callback would never be reached with
  unconfigured secrets anyway — `start` fails first).
- **TDD (red → green):** `test_oauth_not_configured_is_runtimeerror_subclass`
  (MRO), `test_start_oauth_raises_oauth_not_configured_when_secrets_missing`
  (service layer, real `_build_flow`),
  `test_oauth_start_unconfigured_secrets_returns_503_not_500` (route).
- One-line CLAUDE.md note added next to the existing `#120` OAuth
  paragraph in the "DB-canonical accounts + admin CRUD (Sub-plan 2A)"
  section.

### 1. **#125 — method-bound CSRF *mint* helper** *(deferred — do it WHEN the accounts HTML UI lands)*

Tracking note from the PR #124 review. The CSRF *verify* side is
already method-bound (`csrf_action`, #122). The *mint* side is not —
but that's fine **today** because the account-CRUD surface is
API-only (no HTML template mints account-CRUD tokens). When Sub-plan
2A.3 (the accounts Jinja2/HTMX screens) is built, whoever wires the
PATCH/DELETE buttons MUST mint tokens via `csrf_action(method, path)`,
or every mutation 400s with "CSRF token invalid" — and the failure is
silent until a button is clicked. Suggested fix: expose a
method-aware `csrf_token_for(action, method="POST")` to the template
context that applies `csrf_action` internally. **Care:** the existing
`htmx` and `/admin/logout` tokens are verified by `auth_router` via
plain `verify_csrf_token` (NOT `check_csrf`), so the helper must keep
their non-method-bound behaviour (default `method=None` → plain
action, or a separate helper). *Do not start #125 standalone — fold
it into 2A.3.*
